Architecture

The engine's packages and their dependencies, the stages of a frame, and the contract a display backend implements.

Modules

One Go module. Everything except the public pkg/ascdii facade lives under internal/, one package per concern, grouped by module:

internal/engine/
  core/      color, geom, noise, guid, par, prop, input
  render/    cell, raster, braille, texture, view, light, draw, pipeline
  world/     scene (GameObjects, components, references), components, anim, fx,
             physics (2D shapes on the ground plane)
  assets/    asset (catalog, .meta, library, sprites), mesh (OBJ), material, animator
  audio/     sound decoding (WAV, MP3) and the mixer
  script/    vm (Lua: VM, scripts, fields, API)
  platform/  the backend contract, terminal, headless, speaker (sound output)
  runtime/   app, loop, bundle, project (manifest, modules), pack (packages), version
internal/editor/   session, service (the Wails boundary), launch (how ascdii starts the editor),
                   players (finds the ascdii-player binaries builds start from), recent,
                   brand (the program icons)
internal/player/   plays a game in the terminal, for ascdii-player and ascdii play
internal/dragonfall/  the sample: a code module and a package
cmd/      ascdii (CLI; starts the editor), editor (Wails), player (ascdii-player),
          snapshot (PNG renders), docref (component reference for the docs),
          brand (icons and Windows resources), hello
docs/     usage (these pages), nav.py (rewrites their navigation)

Dependencies point one way: core ← render ← world ← script; assets uses core, render and world types, and runtime combines them. The editor and content modules depend on the engine; the engine never depends on them. No package keeps state: registries, libraries and VMs are created at startup and passed in.

A frame

  1. Update. Key handlers, updaters and tickers of every enabled component run; Lua scripts run in one VM per game run, each in its own environment. Animation clips are applied, and the main camera object determines the view.
  2. Geometry. Each renderer component draws into the dot buffer through draw.Context: positions in world units, depth and normals derived, textures sampled per dot.
  3. Lighting and post. Shadows, lights, water, fog, outline and grading run over the dots.
  4. Resolve. Every 2x4 dot block becomes one Braille cell with a foreground and a background color; cell drawers such as sprites and HUDs write on top.
  5. Present. The backend shows the cells.

The platform contract

A backend is two small interfaces in internal/engine/platform:

type Frame struct {
  Cells *cell.Grid      // what a terminal shows
  Dots  *raster.Buffer  // the lit dots under the cells, for pixel backends
  Time  float64
}

type Display interface {
  Open(ctx context.Context) error
  Size() (cols, rows int, err error)
  Present(ctx context.Context, f Frame) error
  Close(ctx context.Context) error
}

type Input interface {
  Events(ctx context.Context) <-chan input.Event  // Event{Key, Down}
}
  • platform/terminal is the raw mode terminal: it diffs cells into ANSI escapes and reads keys. Terminals report no key releases, so input.State treats a press as held for a short window that key repeat extends.
  • platform/headless renders to plain text, ANSI or PNG, for tests and the snapshot tool.
  • runtime/app runs any pair with Engine.RunOn(ctx, display, input).
Adding SDLA window backend would live in platform/sdl: open a window in Open, draw Frame.Dots as pixels or Frame.Cells with a font in Present, and turn window key down and key up events into input.Events. Nothing else in the engine changes.

Sound

The scene context carries an AudioOut: play a sound asset, stop it, change its volume. The terminal player's is the audio mixer read by platform/speaker, injected into runtime/app so that only the player links the sound device. The editor's sends play and stop events to its web view, which plays the files itself.

Modules and packages

A module (project.Module) is Go code: a name and a function that registers component kinds. Modules are compiled into the editor and the player, and a project lists the ones it uses in its manifest; only those are installed into its registry. A package (runtime/pack) is data: assets with .meta files and a pack.json naming the modules they need. Installing a package copies it into packages/<name>/ and adds its modules; see Packages.

Mods

script/vm hosts mods (mods.go). The developer's API script runs in the game's VM and fills a host with the functions, values and events it declares. Each mod gets a Lua state of its own with only the base, string, table and math libraries plus game, log, asset and vec3. A bridge function per API entry copies arguments and results as plain Go data (marshal.go), which drops handles, so no reference into the game crosses. Calls into a mod run under a 50 millisecond context deadline. runtime/project.LoadMods reads the mod folders and loads their assets under mods/<name>/ with asset.Library.LoadUnder; runtime/app starts the mods on the first update, when the scene runs, and the editor does the same when play mode starts.

The editor

editor/session owns the open project, the edited scene, a cloned scene during play, the undo history and the render loop. editor/service is the boundary to the Vue interface: Wails binds its methods, and every error leaves it with a stable code such as not_found: or prefab_locked:. Frames reach the interface as raw bytes from a small HTTP handler rather than as JSON, so a 220 by 60 view remains cheap at 60 frames per second.

The editor is always started by ascdii (editor/launch): ascdii sets ASCDII_LAUNCHER to its own path when it starts the editor, which also tells the editor where to find the players for builds. An editor started without it starts ascdii, which starts the editor again, and exits. Editors built for wails dev skip the check.
